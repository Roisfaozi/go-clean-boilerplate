# Feature Workflow

## Use when

- adding feature behavior to an existing backend module
- adding a new module generated by `make gen-module`
- adding UI support in `apps/web` or `apps/client`
- touching more than one layer of a module

## Read first

- `llm/cache/project-overview.md`
- `llm/cache/architecture.md`
- `llm/cache/module-map.md`
- `llm/cache/domain-rules.md`
- relevant convention files under `llm/conventions/`

## Live code to inspect

- backend composition: `internal/config/app.go`
- route groups: `internal/router/router.go`
- target module: `internal/modules/<module>`
- frontend app: `apps/web` or `apps/client`
- shared frontend packages: `packages/*`
- DB impact: `db/migrations`, affected repository/model files

## Steps

1. classify feature: backend-only, frontend-only, DB-backed, cross-stack, or worker/realtime/upload.
2. identify existing analog module or closest route/controller/usecase/repository pattern.
3. update model/entity/repository/usecase/controller in that order when backend data behavior changes.
4. wire dependencies in module constructor and `internal/config/app.go` only when required.
5. attach route in correct router group and choose API key/JWT/session/tenant/Casbin scope.
6. update frontend proxy/client/types/UI only if active frontend surface needs it.
7. add or update tests at narrowest useful layer.
8. update `llm/tasks/lessons.md` only if a durable repo rule was discovered.

## Verification

- backend narrow: targeted `go test` or `make test`.
- route/security: middleware/module tests plus integration/E2E if auth/tenant/Casbin changes.
- DB: migration checks plus integration tests.
- frontend web: package `typecheck`, `lint`, `build`.
- frontend client: package `typecheck`, `build`, `test:e2e` if route flow changes.

## Output summary

- changed backend modules and route groups
- changed frontend apps/packages
- verification run or skipped with reason
- any follow-up production-readiness notes
